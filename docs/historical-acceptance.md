# Historical capability acceptance criteria

The M1–M8 baseline below preserves the 82 original capability acceptance criteria, without ticket readiness, dependency ordering or agent execution policy. This is historical product/test context, not a live backlog or evidence that a particular revision passed. Current behavior and limits are described in the user handbook, development guide and detailed design contracts. Original identifiers provide provenance; later accepted contracts take precedence where capabilities evolved.

## M1-01 — Establish implementation skeleton

- Repository has documented build/test/lint commands.
- Core packages have one-way dependencies consistent with design docs.
- CLI executable/entry point runs a help command.
- Unit-test infrastructure runs in CI/local environment.
- No VS Code dependency exists in core packages.

---

## M1-02 — Implement source ranges and structured diagnostics

- Multi-line UTF-8 source positions are tested.
- Diagnostics are plain core data, not rendered strings/UI objects.
- Invalid ranges cannot silently enter normal APIs.
- Diagnostic codes are stable identifiers suitable for later code actions.

---

## M1-03 — Define build artifacts and source-map contracts

- Encoder input cannot be raw unvalidated source text.
- Encoded program exposes BASIC line offsets/lengths.
- Contract can associate encoded lines/statements with source ranges.
- TAP wrapping is separate from BASIC-program encoding.

---

## M1-04 — Implement physical-line scanner and line-number validation

- Valid numbered lines produce source-ranged line nodes.
- Duplicate line numbers produce a structured error.
- Missing/malformed line number produces a recoverable diagnostic.
- Ordering policy follows the source-format contract and is tested.
- Scanner never invents implicit line numbers.

---

## M1-05 — Implement recoverable lexer/parser for M1 subset

- Valid M1 fixture parses into CST + semantic-shaped syntax nodes.
- Incomplete/malformed source returns nodes plus diagnostics instead of throwing.
- Keywords inside strings are not tokenized as BASIC commands.
- Source ranges cover tokens/nodes accurately.
- Architecture can add further ROM statements without replacement.

---

## M1-06 — Implement M1 semantic validation and BuildableProgram

- Encoder receives only BuildableProgram.
- Syntax/compatibility errors prevent binary build.
- Warnings do not inherently prevent build.
- No semantic stage reparses source strings.

---

## M1-07 — Research and implement authentic Spectrum numeric encoding

- Algorithm is documented with primary/reference provenance.
- Tests use expected bytes obtained independently of ZXCode.
- Integer and representative non-integer/exponent cases are covered as appropriate.
- No host floating-point byte dump is mistaken for Spectrum representation.

---

## M1-08 — Implement tokenized BASIC program encoder

- Output is deterministic.
- Keyword tokenization is context-correct for supported syntax.
- Strings retain keyword-looking text literally.
- Encoded line metadata maps back to source.
- Unit tests compare exact expected bytes.

---

## M1-09 — Implement TAP writer

- TAP block lengths/flags/checksums are unit-tested.
- BASIC metadata needed for load/autostart policy is explicit.
- TAP writer accepts encoded bytes; it does not know BASIC grammar.
- Exact TAP bytes are testable deterministically.

---

## M1-10 — Implement check/build CLI and orchestration

- `check` reports structured diagnostics in a useful CLI representation and emits no TAP.
- `build` refuses fatal diagnostics and writes a TAP on success.
- Exit status distinguishes success/failure.
- Output path behaviour is documented/tested.
- CLI contains no alternate parser/encoder logic.

---

## M1-11 — Establish independent golden fixture and end-to-end emulator acceptance

- Expected binary did not originate from ZXCode itself.
- Automated test compares exact generated bytes.
- Generated TAP loads in the selected reference emulator as 48K BASIC.
- Running it prints `HELLO WORLD`.
- Procedure is documented sufficiently for another developer/agent to reproduce.

## M2-07 — Implement control flow and static line-target semantics

## M2-08 — Implement FOR/NEXT

authentic FOR variable/range/optional STEP grammar; NEXT variable validation; typing fixtures; no modern loop syntax.

## M2-09 — Research and implement PRINT/LPRINT item grammar

expression items, separators, AT/TAB and formatting controls represented semantically; empty/trailing item cases fixture-tested; LPRINT differences documented; not modeled as generic call arguments.

## M2-10 — Research and implement INPUT grammar

prompts/display items separated from assignable input targets; LINE form supported per ROM; malformed target diagnosed; fixtures derive from authentic syntax.

## M2-11 — Implement arrays, DIM and string slicing

## M2-12 — Research and implement DATA/READ/RESTORE

DATA grammar based on ROM behaviour; READ targets validated; RESTORE optional target semantics correct; DATA preservation sufficient for exact encoding.

## M2-13 — Research and implement DEF FN and FN calls

## M2-14 — Implement REM raw-tail semantics

keyword-like content after REM is not parsed/tokenized normally; raw source range preserved; colon/quote edge cases match ROM fixtures; arbitrary-byte policy deferred to M3 where necessary.

## M2-15 — Implement LIST/LLIST and cassette command grammars

LIST/LLIST accepted forms fixture-driven; SAVE/LOAD/VERIFY/MERGE cassette grammar represented explicitly; no generic-expression-list shortcut.

## M2-16 — Define capability policy for ROM-recognized peripheral commands

parser recognizes authentic forms; diagnostic severity/profile policy documented; default completion policy specified; vocabulary is not falsely labelled “non-48K token”.

## M2-17 — Complete encoder coverage and BASIC-core acceptance corpus

every accepted M2 AST construct has encoding tests; corpus covers graphics, strings, math, input, arrays, DATA, control flow and functions; unsupported syntax fails structurally; no placeholder encoding.

## M8-01 — Research authentic BASIC runtime/debug semantics

- Relevant ROM variables/routines/state documented with primary/reference sources.
- Candidate breakpoint/observation strategy described.
- Colon-separated statements, loops, IF/THEN, GO TO and GO SUB/RETURN considered.
- Unknowns explicitly listed; no source-breakpoint promise yet.

## M8-02 — Evaluate controllable emulator/debug backends

- At least one backend demonstrates programmatic machine control.
- Licensing/platform/transport constraints documented.
- Evidence includes repeatable commands/prototype, not documentation assumption.
- Backend choice may differ from M6 simple-run emulator.

## M8-03 — Define debug-machine adapter/protocol

- Contract separates machine-level pause/resume/memory/breakpoints from BASIC semantics.
- Backend-specific ZRCP details stay in adapter.
- Capability negotiation permits weaker/stronger backends.
- Test-double backend possible.

## M8-04 — Prove source → encoded BASIC → runtime correlation

- Correct source location identified repeatedly for multiple lines.
- Test includes colon-separated statements and control-flow changes.
- Mapping method survives realistic program relocation/base-address conditions.
- Failure modes documented.
- **Gate:** if reliable mapping cannot be proven, redesign M8 before proceeding.

## M8-05 — Integrate selected debug backend and lifecycle

- ZXCode can launch/attach as designed, pause/resume/reset and read required machine state.
- Backend disconnect/restart handled.
- Normal M6 Run remains usable independently.

## M8-06 — Implement BASIC source breakpoints and execution indication

- Breakpoints work on representative BASIC lines/statements.
- False machine-level hits auto-continue safely where design requires.
- Current execution source range shown.
- Stale source/build identity prevents misleading mapping.

## M8-07 — Implement memory and BASIC-variable inspection

- Numeric/string scalar examples inspect correctly.
- Supported arrays/types explicitly documented.
- Raw memory viewer remains available when semantic decoding is unavailable.
- Decoder is fixture-tested against known runtime state.

## M8-08 — Implement screen and watch inspection UX

- Spectrum screen memory can be viewed/refreshed.
- User can watch supported BASIC variables/expressions according to defined semantics.
- Paused/running state is clearly represented.
- UI consumes debug APIs rather than emulator-specific protocol.

## M8-09 — Research BASIC stepping semantics and complete M8 acceptance

- User-facing meaning of each step command documented.
- Implementation tested across loops, IF/THEN, colon statements and subroutines.
- Unsupported semantics are omitted rather than approximated misleadingly.
- End-to-end session can run, break at source, inspect state, perform supported step, continue and reset.
